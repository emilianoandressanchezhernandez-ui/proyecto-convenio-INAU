# Proyecto TheNewfutures — Plataforma de gestión de talleres en convenio con INAU

## Plan de Contingencia

**Rama:** Ciberseguridad  
**Fecha:** 22 de octubre de 2026

## 1. Objetivo y alcance

Este plan establece cómo responder ante incidentes que puedan afectar la disponibilidad del sistema, la integridad de la información o la confidencialidad de las cuentas y los datos gestionados por TheNewfutures/INAU. Se basa en los riesgos documentados del proyecto, la arquitectura PHP–Apache–MySQL, los contenedores Docker y la guía de despliegue del servidor.

La tabla define acciones a realizar, responsables por función y evidencias que deben conservarse. Los tiempos objetivo de recuperación, la frecuencia de respaldo y los responsables personales deben fijarse antes del despliegue real; la documentación actual no establece valores concretos para esos puntos.

## 2. Tabla del plan de contingencia

|---|---|---|---|---|---|---|---|
| PC-01 | La aplicación o la API deja de responder | El sitio no carga, las peticiones HTTP fallan o el contenedor `api` aparece detenido en `docker compose ps`. | Los usuarios no pueden ingresar o utilizar las funciones de la plataforma. | Confirmar el estado de los contenedores y revisar `docker compose logs api`. Evitar cambios simultáneos no documentados. | Corregir la causa identificada y reconstruir/reiniciar el servicio con `docker compose up -d --build` cuando corresponda. Verificar login, perfil y una ruta funcional. | Responsable técnico de la aplicación; coordinador del proyecto informa el estado. | Registrar logs, causa, acciones y hora de recuperación. Cerrar cuando las rutas principales respondan correctamente. |
| PC-02 | MySQL no está disponible | El contenedor `database` está detenido o la API informa errores de conexión. | Interrupción de consultas y operaciones; posibilidad de que algunas funciones no guarden información. | Revisar `docker compose ps` y `docker compose logs database`. No borrar volúmenes ni ejecutar scripts que eliminen la base como primera medida. | Resolver el fallo del servicio o de configuración y comprobar que la API vuelve a conectarse. Cerrar cuando la base esté accesible y las operaciones necesarias funcionen. |
| PC-03 | Pérdida o corrupción de la base de datos | Faltan registros, las tablas no están disponibles o las consultas muestran datos inesperadamente incompletos. | Pérdida de información de usuarios, talleres, inscripciones, asistencias, entregas y adjuntos relacionados. | Detener las tareas que puedan sobrescribir datos. Preservar el estado actual y averiguar si existe un respaldo válido antes de intentar restaurar. | Restaurar un respaldo verificado, si existe. La documentación de despliegue propone generar una copia con `mysqldump` antes de actualizar. Después comprobar tablas y registros críticos. | Responsable de base de datos; coordinador autoriza la recuperación con pérdida potencial de datos. | Identificar el respaldo utilizado, su fecha, los datos restaurados y las diferencias detectadas. No cerrar si no se evaluó la integridad de la información recuperada. |
| PC-04 | Infección por ransomware o compromiso del equipo/servidor | Archivos inaccesibles o modificados, alertas del sistema, actividad inusual o indicios de cifrado no autorizado. | Indisponibilidad de la aplicación y posible pérdida de código, adjuntos o datos. | Aislar el equipo o servidor afectado de la red cuando sea posible; no conectar respaldos al equipo comprometido. Informar al responsable técnico y preservar evidencias. | Reinstalar o reconstruir desde un entorno considerado confiable; recuperar el código desde el repositorio y los datos desde un respaldo verificado. Cambiar las credenciales que pudieran haberse expuesto. | Responsable de infraestructura y coordinador del proyecto. | Registrar sistemas afectados, decisiones, copias revisadas y pruebas realizadas antes de reabrir el servicio. |
| PC-05 | Exposición de `SECRET_KEY` o credenciales de MySQL | Se detecta una clave en código versionado, un archivo `.env` compartido o configuración expuesta. | Posible falsificación de JWT, accesos no autorizados o conexión a la base de datos. | Tratar el secreto como comprometido; limitar accesos mientras se evalúa el alcance. No reutilizar la clave publicada. | Generar una clave nueva y credenciales nuevas; actualizar las variables del entorno, reiniciar el servicio y verificar que los tokens firmados con la clave anterior ya no se aceptan. Revisar el acceso a la base de datos. | Responsable técnico de seguridad/infraestructura. | Registrar qué secreto se rotó, qué entornos se actualizaron y el resultado de las verificaciones. No copiar valores secretos en el informe del incidente. |
| PC-06 | Compromiso de una cuenta por phishing o robo de credenciales | Actividad atribuible a un usuario que este no reconoce, acceso inesperado o reporte del propio usuario. | Acceso no autorizado a información personal y funciones del rol comprometido. | Bloquear o deshabilitar la cuenta si las funciones de administración disponibles lo permiten; identificar el alcance y preservar los registros existentes. Avisar al responsable del sistema. | Restablecer la credencial por el procedimiento administrativo disponible, verificar el rol y revisar cambios realizados. Si se sospecha de un token robado, tener presente que el JWT tiene una caducidad configurada y que borrar la cookie del navegador no revoca necesariamente una copia ya robada. | Administrador autorizado y responsable técnico. | Registrar cuenta afectada, período investigado, cambios revertidos y confirmación del usuario. Cerrar al reducir el acceso no autorizado y verificar la cuenta. |
| PC-07 | Acceso a una ruta restringida con un rol incorrecto | Una prueba autorizada obtiene datos o permite una operación que debería rechazar por rol o pertenencia a un taller. | Exposición o modificación no autorizada de datos de alumnos, talleristas, asistencias o entregas. | Detener las pruebas o acciones afectadas; guardar solicitud, ruta, rol y respuesta sin incluir contraseñas ni tokens completos. | Revisar la definición de la ruta en `backend/api-completa/routes.php`, los controles de `core/AuthMiddleware.php` y la validación de permisos del Service implicado. Corregir y repetir pruebas con roles autorizados y no autorizados. | Responsable técnico del backend; administrador de prueba verifica los roles. | Conservar casos de prueba y respuestas esperadas. Cerrar cuando el acceso autorizado funciona y el no autorizado recibe rechazo adecuado. |
| PC-08 | Se detecta un puerto inesperadamente accesible en el escaneo Nmap | El escaneo muestra `open` en un puerto que no debería estar disponible desde ese origen, especialmente MySQL o acceso directo a la API. | Mayor superficie de ataque y posibilidad de conexión directa a servicios internos. | Registrar IP objetivo, puerto, origen, fecha y salida de Nmap. No intentar explotar el servicio; avisar a infraestructura. | Revisar el firewall y los mapeos de `ports` del Compose. Limitar MySQL a acceso local o interno y mantener el acceso público a través de los puertos web requeridos. Volver a escanear desde el mismo punto autorizado. | Responsable de infraestructura; responsable técnico confirma la función del servicio. | Adjuntar los resultados antes y después. Cerrar cuando la exposición coincide con la política de puertos acordada. |
| PC-09 | Posible XSS a través de información ingresada en formularios | Se observa contenido que se interpreta como HTML/JavaScript, ejecución inesperada en el navegador o reporte de un usuario. | Alteración de la interfaz, exposición de datos accesibles en el navegador o abuso de la sesión del usuario. | Evitar usar la pantalla afectada y no ingresar datos sensibles mientras se investiga. Registrar página, campo y pasos reproducibles sin distribuir código malicioso a otros usuarios. | Localizar el punto donde el dato se valida y representa; priorizar `textContent` o escape apropiado para texto, y verificar tanto los datos propios como los recuperados desde la API. Repetir una prueba controlada. | Responsable técnico del frontend/backend. | Registrar la página afectada, la corrección y el caso de regresión. Cerrar cuando el texto de prueba se muestre como texto y no se ejecute. |
| PC-10 | Se carga o no se puede descargar un adjunto no esperado | El archivo es rechazado por la validación, no se encuentra en el almacenamiento o la descarga falla. | Entrega incompleta, indisponibilidad de material o posible exposición de un archivo. | Registrar el ID del adjunto/contenido, tipo MIME informado y error sin divulgar públicamente archivos. No desactivar la validación para resolver el problema. | Revisar `validators/AdjuntoValidator.php`, `services/AdjuntoService.php`, los permisos de almacenamiento y la configuración PHP de carga. Revalidar el tipo y el tamaño antes de repetir la operación. | Responsable técnico del backend y responsable de la funcionalidad. | Registrar archivo de prueba, respuesta del sistema y resultado de la nueva carga/descarga. Cerrar cuando los archivos permitidos se procesan y los no permitidos son rechazados. |
| PC-11 | Actualización defectuosa de la aplicación o del entorno Docker | Tras un cambio dejan de iniciar contenedores, aparecen errores en logs o falla una función previamente operativa. | Interrupción del servicio o incompatibilidad de aplicación y base. | Detener nuevas actualizaciones y conservar logs y versión desplegada. No ejecutar `docker compose down -v` como solución genérica, porque elimina los volúmenes de datos. | Corregir la configuración o volver a una versión conocida del código. Restaurar datos solo si existe un respaldo válido y es necesario. Verificar API, base y login antes de reabrir. | Responsable de despliegue/infraestructura. | Registrar commit o versión, comandos ejecutados, estado de la base y prueba funcional posterior. |
| PC-12 | El almacenamiento de adjuntos deja de estar disponible o se pierden archivos | Un adjunto se registra en la base pero no puede descargarse, o no existe el archivo físico esperado. | Materiales y entregas no disponibles aunque los metadatos permanezcan guardados. | Evitar borrar registros o volver a subir archivos con el mismo nombre sin comprobar la causa. Revisar el volumen `uploads_data` y los logs. | Recuperar el almacenamiento persistente si existe una copia válida y verificar la correspondencia entre registros de adjuntos y archivos físicos. | Responsable de infraestructura y responsable técnico de la aplicación. | Registrar adjuntos afectados y las pruebas de lectura/descarga realizadas. Cerrar cuando los adjuntos críticos se verifiquen o se documente cuáles no pudieron recuperarse. |

## 3. Procedimiento común de respuesta

| Fase | Acción obligatoria | Resultado esperado |
|---|---|---|
| 1. Detección | Recibir el aviso, confirmar la señal y anotar fecha/hora. | Incidente identificado y registrado. |
| 2. Clasificación | Identificar los servicios, cuentas, datos y funciones afectados. | Alcance inicial documentado. |
| 3. Contención | Evitar que el incidente continúe o que una corrección improvisada destruya evidencia o datos. | Riesgo inmediato reducido. |
| 4. Recuperación | Aplicar la solución del escenario; usar solo copias verificadas cuando se necesite restaurar datos. | Servicio recuperado de forma controlada. |
| 5. Verificación | Probar accesos por rol, API, base de datos y funciones relacionadas con el incidente. | Evidencia de que la corrección funciona. |
| 6. Cierre | Registrar causa, impacto, acciones, resultado y tareas posteriores. | Historial disponible para revisión del equipo. |

## 4. Contacto, asignación y criterios operativos

| Elemento | Definición para este proyecto |
|---|---|
| Coordinación del incidente | El coordinador del proyecto organiza la comunicación del equipo y mantiene el registro del incidente. |
| Diagnóstico técnico | La persona responsable del backend, Docker, base de datos o frontend actúa sobre el componente afectado. Si no existe una asignación formal, debe definirse antes del despliegue. |
| Comunicación | Informar al equipo y a la persona que coordina el proyecto. Si hay datos personales comprometidos, no compartirlos por canales innecesarios y limitar el detalle al personal que deba intervenir. |
| Respaldos | La guía de despliegue recomienda crear una copia de la base antes de cada actualización mediante `mysqldump`. No se debe suponer que existe un respaldo automático ni que una copia es recuperable hasta verificarla. |
| Objetivos de recuperación | El repositorio no fija RTO (tiempo objetivo de recuperación) ni RPO (pérdida máxima de datos aceptable). Deben acordarse con el responsable del proyecto antes del uso real. |
| Aprobación de reapertura | El responsable técnico confirma las pruebas del componente y el coordinador verifica que el incidente esté registrado y comunicado. |
