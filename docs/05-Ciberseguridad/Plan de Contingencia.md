# Proyecto TheNewfutures — Plataforma de gestión de talleres en convenio con INAU

## Plan de Contingencia

**Rama:** Ciberseguridad  
**Fecha:** 22 de octubre de 2026  
**Última actualización:** 26 de octubre de 2026

## 1. Objetivo y alcance

Este plan establece cómo responder ante incidentes que puedan afectar la disponibilidad del sistema, la integridad de la información o la confidencialidad de las cuentas y los datos gestionados por TheNewfutures/INAU. Se basa en los riesgos documentados del proyecto, la arquitectura PHP–Apache–MySQL, los contenedores Docker y la guía de despliegue del servidor.

La tabla define acciones a realizar, responsables por función y evidencias que deben conservarse. Los responsables de cada función se asignan en la sección 4. Los tiempos objetivo de recuperación y la frecuencia de respaldo deben fijarse antes del despliegue real; la documentación actual no establece valores concretos para esos puntos.

Avisar al responsable del sistema. | Restablecer la credencial por el procedimiento administrativo disponible, verificar el rol y revisar cambios realizados. Si se sospecha de un token robado, tener presente que el JWT tiene una caducidad configurada y que borrar la cookie del navegador no revoca necesariamente una copia ya robada. Desactivar la cuenta tampoco corta un token ya emitido: el middleware no consulta el estado del usuario en cada petición, por lo que el acceso continúa hasta que el token vence (una hora por defecto, según `TOKEN_LIFETIME`). Ver `Mecanismos_Autenticacion_Criptografia_INAU.md`, sección 9. | Administrador autorizado y responsable técnico. | Registrar cuenta afectada, período investigado, cambios revertidos y confirmación del usuario. Limitar MySQL a acceso local o interno y mantener el acceso público a través de los puertos web requeridos. Volver a escanear desde el mismo punto autorizado. | Responsable de infraestructura; responsable técnico confirma la función del servicio. | Adjuntar los resultados antes y después. Cerrar cuando la exposición coincide con la política de puertos acordada. **Caso registrado (24 y 25/10/2026):** Nmap encontró abiertos la API (8002) y MySQL (3308) en el servidor de prueba, aunque el firewall no los permitía. ## 3. Procedimiento común de respuesta

| Fase | Acción obligatoria | Resultado esperado |
|---|---|---|
| 1. Detección | Recibir el aviso, confirmar la señal y anotar fecha/hora. | Incidente identificado y registrado. |
| 2. Clasificación | Identificar los servicios, cuentas, datos y funciones afectados. | Alcance inicial documentado. |
| 3. Contención | Evitar que el incidente continúe o que una corrección improvisada destruya evidencia o datos. | Riesgo inmediato reducido. |
| 4. Recuperación | Aplicar la solución del escenario; usar solo copias verificadas cuando se necesite restaurar datos. | Servicio recuperado de forma controlada. |
| 5. Verificación | Probar accesos por rol, API, base de datos y funciones relacionadas con el incidente. | Evidencia de que la corrección funciona. |
| 6. Cierre | Registrar causa, impacto, acciones, resultado y tareas posteriores. | Historial disponible para revisión del equipo. |

## 4. Contacto, asignación y criterios operativos

| Elemento | Definición para este proyecto |
|---|---|
| Coordinación del incidente | El coordinador del proyecto organiza la comunicación del equipo y mantiene el registro del incidente. |
| Diagnóstico técnico | La persona responsable del componente afectado actúa sobre él, según la asignación siguiente. |
| Asignación de responsables | Ver la tabla a continuación. |
| Comunicación | Informar al equipo y a la persona que coordina el proyecto. Si hay datos personales comprometidos, no compartirlos por canales innecesarios y limitar el detalle al personal que deba intervenir. |
| Respaldos | La guía de despliegue recomienda crear una copia de la base antes de cada actualización mediante `mysqldump`. Esa copia no incluye los archivos adjuntos, que se respaldan aparte desde el volumen `uploads_data` (comando a continuación). No se debe suponer que existe un respaldo automático ni que una copia es recuperable hasta verificarla. |
| Objetivos de recuperación | El repositorio no fija RTO (tiempo objetivo de recuperación) ni RPO (pérdida máxima de datos aceptable). Deben acordarse con el responsable del proyecto antes del uso real. |
| Aprobación de reapertura | El responsable técnico confirma las pruebas del componente y el coordinador verifica que el incidente esté registrado y comunicado. |

### Respaldo de los archivos adjuntos

Desde `backend/api-completa`, en el servidor:

```bash
docker run --rm -v api-completa_uploads_data:/datos -v "$PWD":/respaldo alpine tar czf /respaldo/uploads_$(date +%F).tar.gz -C /datos .
```

El nombre del volumen (`api-completa_uploads_data`) corresponde al proyecto de Compose de la carpeta `api-completa`; puede comprobarse con `docker volume ls`.
